## What We've Built (and Why It Already Matters)

greed-compute started as "ChatGPT Code Interpreter as an API." It is now something more specific and more valuable: **the only compute platform that treats a Python interpreter as a versioned, forkable, shareable object**.

The innovations shipped so far are not incremental improvements on E2B or Daytona. They are a different category of primitive:

| Innovation | What it is | Why nobody else has it |
|---|---|---|
| **CALF** | Checkpoint a running interpreter; fork N workers from it in ~10ms | Everyone else cold-starts every worker, every time |
| **Speculative Session Hydration** | Pre-warm workers while template is still running | Requires knowing that forks are coming; stateless platforms can't do this |
| **StAR** | Streaming reduce — results flow in as each worker finishes, not after the last | Requires a persistent reducer session; stateless platforms can't hold one |
| **SAW** | Multiple agents (any model) share one live Python interpreter | Requires serialized access + auto-checkpointing; no other platform has a "workspace" primitive |
| **cuntext** | LLM-native API documentation fragments served at `/v1/cuntext/*.cuntext` | No other compute platform treats LLMs as first-class API consumers |

These are not features. They are **primitives** — the kind of thing that, once invented, other systems have to build on top of rather than replicate.

The current stack is production-grade: nsjail OS-level isolation, dill-based interpreter serialization, credits-based billing (1 credit = 1 exec-second), Stripe-powered tiers (hobby/builder/scale), GitHub OAuth, SSE streaming, background jobs with webhook callbacks, and a deployed API at `compute.deep-ml.com`.

Phase 1 is done. The question this document answers is: **what does Phase 2 look like, and why does it matter to acquirers?**

## The Market as of Mid-2026

The sandbox/agent-compute space has consolidated around four archetypes:

### Archetype 1: Fast Isolation (E2B, Fly Sprites, Zeroboot)
Firecracker microVMs, sub-200ms cold starts, strong hardware isolation. The story is security and speed. E2B serves 200M+ sandboxes, raised $21M Series A, growing 375x YoY. **Weakness:** stateless by design, no ML awareness, per-hour pricing punishes bursty agent workloads, no shared state between agents.

### Archetype 2: Agent-Native Speed (Daytona)
Sub-60ms provisioning via copy-on-write filesystem forks. $24M Series A (February 2026, Datadog strategic). Snapshot/pause/fork primitives. Explicitly building "agent-native compute infrastructure." **Weakness:** generic filesystem-level forking, not Python-interpreter-level; no ML primitive colocation; no multi-agent shared state.

### Archetype 3: Git-for-Compute (Morph Labs)
Infinibranch / Liquid Metal: fork a running VM to dozens of instances in milliseconds. Sub-100ms VM startup, sub-200ms state snapshot. CEO Jesse Han frames it as "reversible compute" — agents explore parallel execution paths during their own reasoning process. GPU support shipped Q4 2025. **Weakness:** VM-level granularity (expensive, heavyweight); no Python-specific primitives; no ML colocation; no multi-agent workspace.

### Archetype 4: ML-Native Serverless (Modal Labs)
$80M Series B, ~$1B valuation. GPU-first, infrastructure-from-code via Python decorators, elastic scaling to 20,000 concurrent containers. The ML developer's home. **Weakness:** stateless; no persistent interpreter; no agent coordination primitives; no forkable compute.

### Where We Sit

greed-compute is not in any of these archetypes. It operates one level up the stack from all of them:


Every competitor is building the execution substrate. We are building the **interpreter layer** — the abstraction that agents actually reason about. The substrate is a commodity; the interpreter layer is not.

This is the architectural bet that defines everything else.

## Architecture: The Next Four Layers

The current architecture is three layers: API gateway (Rust/Axum), session orchestrator, Python sandbox. The vision adds four more layers above and around those three. Each layer is independently valuable and compounds with the others.

### Layer 4: Reactive Compute Engine

**The problem:** Every agent compute platform today is pull-based. To trigger an agent when a file appears, a webhook fires, or another agent completes, you build your own glue. This is the Polling Tax — teams write cron jobs and webhook servers to compensate for absent platform primitives.

**The primitive:**

```
POST /v1/triggers
{
  "type": "webhook" | "cron" | "session_event" | "workspace_event",
  "session_id": "...",             // which session to wake
  "condition": { ... },            // what to match
  "code": "handle_event(event)"    // what to execute on wake
}
```

A trigger attaches to a **hibernated session**. When the event fires, the session wakes (via CALF restore from checkpoint), executes the registered code with the event payload injected, and returns to hibernation. Zero cost while waiting.

**Why this compounds with CALF:** hibernated sessions are just checkpoints. Waking one is a CALF fork. Reactive execution is free once CALF exists — we just need the trigger routing layer.

**Implementation:** A `triggers` table in SQLite (event_type, match_condition, session_id, code). A trigger dispatcher task that receives events (HTTP webhook, internal session events) and fires the matching session. Use the existing background job infrastructure.

### Layer 5: Agent Identity and Memory Substrate

**The problem:** Every agent run today is a fresh identity. An agent that learned something yesterday has no way to access that learning today — unless the application developer builds memory explicitly on top. No platform provides persistent agent identity or native memory.

**Two primitives:**

**5a. Agent Identity**

```
POST /v1/agents
{ "name": "data-analyst-01", "permissions": [...] }

→ { "agent_id": "agent_abc123", "api_key": "greed_agent_..." }
```

An agent identity is a durable entity in the database. It has:
- Its own API key (not the human's key — capability separation)
- A namespace for memory storage
- Usage tracking scoped to the agent, not the human
- Permission scope: which session templates, which workspace access, which max execution time

This is not authentication theater. It enables **cost attribution** (which agent is spending what), **quota enforcement** (this agent can spend 100 credits/day), and **capability delegation** (Agent A spawns Agent B with a subset of its own permissions — Agent B cannot exceed Agent A's rights).

**5b. Memory Tiers**

```
# Write to memory (from within a session)
platform.remember("key", value, tier="warm")  # persists across sessions
platform.remember("learned", summary, tier="cold")  # semantic, long-lived

# Read from memory (auto-injected into session context)
platform.recall("key")
platform.search("similar to: user prefers concise output")  # semantic search
```

Three tiers, managed by the platform:

| Tier | Storage | Retrieval | Eviction |
|---|---|---|---|
| **Hot** | In-session variables | Instant (in-memory) | On session end |
| **Warm** | SQLite JSON blob per agent | By key, <1ms | TTL or capacity |
| **Cold** | Embedding vectors per agent | Semantic similarity, <50ms | Priority-based |

The warm tier is a simple key-value store scoped to an agent identity — one table, one index. The cold tier is embeddings computed at write time (via a local sentence-transformers model or proxied to an embeddings API) stored in a per-agent namespace. Retrieval is cosine similarity over the agent's namespace.

**Why this matters:** memory is the moat. Once an agent's learned behavior (preferences, domain knowledge, past mistakes) lives in the platform, switching to a competitor means losing that history. This is not a feature; it is lock-in that agents actively want.

### Layer 6: Interpreter-Colocated ML Primitives

**The problem:** agents that need embeddings call OpenAI's embedding API, get vectors back, store them in a separate Pinecone instance, query it with another API call. Three network round-trips for what should be one local operation. The same pattern applies to fine-tuning, model inference, and similarity search.

Modal is the closest to solving this — it colocates ML workloads — but Modal is stateless. We have the stateful interpreter. Adding ML primitives to it is structurally different from what Modal offers.

**Four primitives:**

**6a. Embed (in-process)**

```python
# From inside a greed-compute session
vecs = platform.embed(["text one", "text two"])  # returns np.ndarray
```

Implementation: a sentence-transformers model (all-MiniLM-L6-v2, 80MB) loaded once per worker pool in a shared process. Batched inference, results returned as numpy arrays. Zero network cost. For GPU tier, use a quantized BAAI/bge model.

**6b. Vector Store (per-agent namespace)**

```python
platform.store("doc-123", vec, metadata={"source": "pdf"})
results = platform.search(query_vec, top_k=5, filter={"source": "pdf"})
```

Implementation: SQLite with sqlite-vec extension (already production-proven, <1MB binary, cosine similarity in SQL). One table per agent namespace. No Pinecone. No Weaviate. No infra overhead.

**6c. Fine-tune from Trajectories**

Every successful agent execution is a (input, output) pair. Collect enough of them and you have a fine-tuning dataset.

```
POST /v1/finetune
{
  "agent_id": "agent_abc123",
  "base_model": "Qwen2.5-Coder-1.5B",
  "method": "lora",
  "auto_collect": true   // use sessions marked as "successful" by outcome
}
```

Implementation: background job that pulls trajectories for the agent, formats them as SFT pairs, runs a LoRA fine-tune using Hugging Face PEFT on a GPU worker (same infrastructure as execution workers, just GPU-flagged), and saves the adapter. The adapter is then available as a `template` option:

```
POST /v1/sessions
{ "template": "my-finetuned-coder", "adapter": "finetune_xyz" }
```

This closes the feedback loop. The platform gets better at the agent's specific task over time, automatically.

**6d. Local Model Inference**

```python
# From inside a session — zero network hop
result = platform.generate("Summarize this data: " + str(df.describe()))
```

Implementation: serve a small open-weight model (Qwen2.5-1.5B or Phi-3-mini) per worker pool via llama.cpp. The `platform.generate()` call is a local socket call — microseconds of overhead, not hundreds of milliseconds of network latency. The business model here is not competing with OpenAI — it is providing inference that is private (no data leaves the sandbox), fast (no network), and predictable (no rate limits).

### Layer 7: Observability and Verified Execution

**The problem:** agents fail silently. A session runs, returns an error, and the developer has a stack trace — but no record of what reasoning led to the bad code, which tool calls preceded it, or what the interpreter state was at the moment of failure. Existing observability tools (LangSmith, Helicone, Braintrust) are separate from the execution substrate; they see the LLM calls but not what happens inside the sandbox.

We are the sandbox. We see everything.

**Three primitives:**

**7a. Execution Spans**

Every execute call becomes a span:

```json
{
  "span_id": "span_abc",
  "session_id": "sess_xyz",
  "agent_id": "agent_123",
  "code": "df.groupby('category').mean()",
  "result": "...",
  "duration_ms": 12,
  "memory_before_mb": 210,
  "memory_after_mb": 215,
  "new_variables": ["result"],
  "parent_span": "span_789"
}
```

Spans are stored in SQLite. A `GET /v1/sessions/{id}/trace` endpoint returns the full execution tree for a session. The trace viewer is the single most useful debugging tool we can give agent developers.

**7b. Checkpoint-Based Replay**

Because CALF lets us fork from any checkpoint, we can replay any past execution:

```
POST /v1/sessions/{id}/replay
{ "from_checkpoint": "ckpt_abc", "code": "df.groupby('category').mean()" }
```

This executes the code against the exact interpreter state that existed at `ckpt_abc`. The developer can try different code against the exact same state that caused a bug. This is time-travel debugging for agent code — nothing like it exists anywhere.

**7c. Tamper-Evident Audit Log**

For regulated industries: every span is hashed (SHA-256 over span content + previous hash, chain-of-custody style). The audit log is append-only. A `GET /v1/sessions/{id}/audit` endpoint returns the hash chain. An external auditor can verify that no execution was modified or deleted after the fact.

This is the primitive that unlocks financial, legal, and healthcare use cases. SOC 2 Type 2 requires audit trails. We can provide one that is mathematically verifiable, not just "we promise we kept the logs."

## The Acquisition Thesis

Anthropic acquired Bun in early 2026. The stated reason was infrastructure reliability — Claude Code depends on Bun; if Bun breaks, Claude Code breaks. The real reason is the one they didn't state: **owning the execution layer below your model is a structural advantage**.

When Anthropic owns Bun, they can optimize the entire path from Claude inference → JavaScript execution. The model and its runtime are co-designed. No competitor can replicate that without acquiring the same layer.

The same logic applies here, but one layer deeper.

**What we have that a foundation model lab cannot easily build:**

1. **A working persistent interpreter layer** — not a design doc, not a prototype, but a production API serving real executions at `compute.deep-ml.com`. The engineering required to build CALF, StAR, and SAW correctly (serialization correctness, concurrency safety, eviction policy) is 6-12 months of work for a team starting from scratch.

2. **Agent-native primitives with no equivalent** — SAW (shared interpreter across models), CALF (fork interpreter state like git), StAR (streaming reduce for agent swarms). These are novel. Morph Labs is the only other company thinking at this level of abstraction, and they are operating at VM granularity, not interpreter granularity.

3. **The cuntext distribution channel** — by making the API natively consumable by LLMs (serving documentation as `.cuntext` fragments that agents can fetch and act on), we have a channel that bypasses human developer adoption entirely. An LLM can discover and use the API without any human reading the docs. This is structurally different from how every other API distributes itself.

4. **The memory moat** — once agent memory lives in the platform (warm + cold tiers tied to agent identity), the switching cost is not "learn a new API" but "lose everything your agent has learned." This is the same moat that made Salesforce sticky for CRM. The platform becomes the system of record for agent knowledge.

**The acquirer map:**

| Acquirer | Why they want us | What they get |
|---|---|---|
| **Anthropic** | Claude Code needs a persistent compute layer; Claude agents need a workbench | Execution layer for all Claude agents; RL training loop from agent trajectories; SAW enables Claude ↔ Claude multi-agent workflows |
| **OpenAI** | Codex/Operator needs a stateful Python environment; Windsurf acquisition ($3B) shows appetite for vertical integration | Persistent interpreter for GPT agents; CALF enables parallel Codex execution at scale; memory layer for ChatGPT plugins |
| **Google/DeepMind** | ADK + Vertex AI Agent Engine are framework plays; they lack an interpreter-layer primitive | Agent-native compute for Gemini; colocated inference + execution eliminates the round-trip tax; EU data residency opens regulated verticals |
| **Datadog** | Strategic investor in Daytona; facing existential threat from AI-native observability tools | First-party telemetry over every agent execution — they see what happens inside the sandbox, not just the API calls around it |
| **Deep-ML** | Already the first customer (internal use for ML challenges) | Complete agent infrastructure for the platform; greed-compute becomes the engine powering all Deep-ML agent workflows |

**The trigger:** the acquisition becomes compelling when we have:

1. **Developer distribution** — 100K+ sandbox executions/month, embedded in agent workflows that teams depend on
2. **Memory layer live** — agents storing and retrieving memories; switching cost becomes real
3. **RL loop closed** — agent trajectories flowing into fine-tuning; any lab that runs agents on our platform is training data we hold
4. **Audit trail shipped** — SOC 2 Type 2 in progress; unlocks Fortune 500 sales and makes us defensible in the compliance conversation

We are 2-3 of these four criteria away from being an acquisition conversation. The roadmap above closes that gap in 24-36 weeks.

## The Single Strategic Bet

Every decision in this roadmap flows from one bet:

> **The interpreter layer — not the VM layer, not the container layer — is where agent infrastructure gets decided. Whoever owns the persistent, forkable, shareable Python interpreter owns the workbench that AI agents actually work on.**

E2B, Daytona, and Morph are racing to build faster VMs. That race commoditizes. The winner will be whichever hyperscaler buys them and runs at loss-leader pricing.

We are building one layer up — the interpreter, the memory, the identity, the ML primitives — on top of whatever substrate wins. Today that substrate is nsjail + subprocess. Tomorrow it might be Firecracker or Morph's Liquid Metal. We don't care, because our value is not in the substrate. It is in what we put on top of it.

The AI has the brain. We give it the workbench.
